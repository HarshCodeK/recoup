# Interview Q&A — Recoup

## The 30-second pitch

"Recoup is a reconciliation control plane for multi-source payment data. It
normalizes five source shapes, matches deterministically first, uses a bounded
probabilistic matcher second, classifies the remaining exceptions, and sends
only ambiguous exceptions to an LLM for typed triage. Recovery is still
deterministic and policy-gated; the LLM never gets a money-execution path."

## Q: Why put the LLM in diagnosis but not recovery?

A: Diagnosis is a classification problem where a wrong answer can be reviewed.
Recovery is a financial-control problem where a wrong answer can move money.
The LLM therefore gets structured evidence and can return REFUSED, while the
recovery playbook and policy engine remain deterministic and independent.

## Q: How do you stop an LLM from moving money?

A: There is no money tool in the diagnosis provider interface. The LLM output is
parsed into a typed Diagnosis, and malformed or low-confidence output becomes
REFUSED. recovery.py maps exception reasons to deterministic action types, and
policy_engine.py decides whether a proposal is allowed. The repository also
has no outbound payment/refund execution path.

## Q: What are the actual policy limits?

A: The current default policy uses a ₹100 economic floor, a ₹10,000 maximum
recovery amount, and at most 3 recovery attempts per event. A duplicate-fire
reason is never auto-recovered. The policy returns an idempotency key with each
decision.

## Q: Why integer paise?

A: Financial arithmetic should not depend on floating-point representation.
Normalized amounts are integer paise; division by 100 is only used when
formatting INR for display.

## Q: How does matching work?

A: The pipeline applies deterministic rules first. Remaining transactions go
through a bounded probabilistic matcher using amount, date, reference, and
counterparty signals. Candidate generation is bucketed by amount to avoid
blind O(N²) pairing, and accepted candidates are assigned greedily best-first.

## Q: Why not use embeddings for matching?

A: This project is deliberately bounded. The current matcher uses interpretable
signals and reference-token similarity rather than introducing a learned
embedding model. For the synthetic evaluation this keeps the behavior easy to
inspect. A real deployment would need evaluation on real transaction data
before choosing a more complex matcher.

## Q: What does the evaluation dataset represent?

A: It is synthetic and generated deterministically with seed=42 at 3,000
transactions by default. It is useful for regression testing and comparing
algorithm changes, not evidence of production reconciliation quality.

## Q: Why did the README retire the old 0.674 / 0.999 / 0.805 figures?

A: Those were computed over transaction IDs rather than unordered matched pairs.
That could give credit for selecting the right transactions but pairing them
incorrectly. The evaluator now compares predicted transaction pairs directly
with ground-truth pairs. The current pair-level metrics must be regenerated by
running PYTHONPATH=. python eval.py; I would not quote the retired numbers.

## Q: Was the evaluation run with a real LLM?

A: The reproducible default evaluation uses StubProvider() so the run does not
depend on network access. The stub intentionally returns REFUSED. The repository
also contains an OpenAI-compatible provider and a live smoke script for exercising
a configured real model, but live-provider results are not the reproducibility
baseline.

## Q: How does the diagnosis layer handle malformed model output?

A: It first tries strict JSON, then a fenced JSON block, then the first balanced
top-level object. If parsing still fails, or if the class is invalid, or if
confidence is below 0.5, the result becomes REFUSED instead of being silently
coerced into a confident diagnosis.

## Q: What is the state machine protecting?

A: state_engine.py defines legal transaction transitions and keeps UNKNOWN
explicit. The point is to prevent "we didn't know" from silently becoming
"retry" or "success". State changes are deterministic; the LLM does not choose
them.

## Q: What does the audit chain prove?

A: Each event hash includes the previous event hash, so changing a later event
breaks verification. That makes the log tamper-evident. It does not by itself
prove that every application path emitted every possible event; the evaluator
and MCP server are separate execution paths with different persistence
behavior.

## Q: What persists?

A: The MCP server can use a persistent SQLite event store for transaction
timelines and chain verification. The evaluation deliberately uses an
in-memory event store so the deterministic run is isolated and reproducible.
There is no production customer or merchant database.

## Q: What does the MCP layer actually expose?

A: Five tools: reconcile a synthetic batch, inspect exceptions, replay a
transaction's audit timeline, test a recovery proposal, and verify the audit
chain. propose_recovery is a policy test; it does not execute a payment or
refund.

## Q: What would you fix before production?

A: First, add a real source adapter and authenticate/rate-limit the MCP boundary.
Then validate against real reconciliation output, add a durable multi-process
audit store, and build a real recovery-execution integration with explicit human
approval and idempotency. The current repository deliberately stops before those
production boundaries.

## Q: How is this tested?

A: The repository currently reports 162 offline pytest tests. They cover the
normalization/matching pipeline, policy invariants, provider behavior, MCP
persistence/replay behavior, and audit-chain integrity. The synthetic evaluation
is a separate regression harness rather than part of the test count.
